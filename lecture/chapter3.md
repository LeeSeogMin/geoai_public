# 3장 데이터를 어디서 찾고, 어떤 규칙 아래 써야 할까 (학부 강의용)

> 이 장에 나오는 검색 결과 개수, 파일 크기, 읽기 시간은 모두 `practice/chapter3/`의 코드를 실제로 실행해 얻은 값이다. 예시를 위해 지어낸 숫자는 없다.

## 1. 오늘의 큰 질문

- 위성영상과 공간데이터는 많다는데, 왜 필요한 자료를 찾는 일은 여전히 어렵게 느껴질까?
- 공개 데이터라고 해도 왜 그냥 내려받아 마음대로 쓰면 안 될까?

GeoAI를 처음 배우면 보통 모델이나 분석 기법부터 떠올리기 쉽다. 그런데 실제 프로젝트에서는 그보다 앞에서 자주 막힌다. 어떤 데이터를 써야 하는지 모르고, 찾더라도 형식이 낯설고, 써도 되는지까지 다시 확인해야 한다. 그래서 이 장은 모델보다 먼저 **데이터를 찾는 질서**, **데이터를 읽는 질서**, **데이터를 쓰는 질서**를 다룬다.

이 세 가지가 정리되지 않으면 이후 장에서 아무리 좋은 분석 방법을 배워도 작업이 이어지지 않는다. 반대로 이 질서가 잡히면, 공개 데이터만으로도 꽤 많은 GeoAI 실험과 정책 분석이 가능해진다.

## 2. 직관적 비유

- **공개 데이터 포털 = 거대한 창고**다. 물건은 많지만, 어디 선반에 무엇이 있는지 모르면 찾는 데 시간이 오래 걸린다.
- **STAC = 창고의 공통 라벨 체계**다. 상자마다 제멋대로 적혀 있던 이름표를 비슷한 방식으로 붙여 둔 것이다.
- **COG, Zarr, GeoParquet = 책 전체를 복사하지 않고 필요한 페이지만 펼쳐 보는 방식**이다.
- **거버넌스 = 출입 규칙과 사용 규칙**이다. 창고에 들어갈 수 있어도, 모든 물건을 마음대로 가져가거나 다시 팔 수 있는 것은 아니다.

이 비유를 머리에 두고 보면 3장의 개념이 훨씬 단순해진다. 결국 물어야 할 것은 세 가지다.

1. 어디에 있는가?
2. 어떻게 찾는가?
3. 어떻게 써야 하는가?

## 3. 핵심 개념 5가지

1. **공개 데이터는 많지만, 데이터마다 잘하는 질문이 다르다.** Landsat, Sentinel-2, MODIS는 모두 위성영상이지만 해상도와 재방문 주기가 다르다.
2. **STAC는 위성데이터 검색을 통일하려는 구조다.** Catalog, Collection, Item, Asset 네 단계로 생각하면 된다.
3. **클라우드 네이티브 포맷은 속도를 바꾸는 약속이다.** 전체 파일을 전부 받지 않고 필요한 부분만 읽게 만든다.
4. **메타데이터와 품질 정보는 재현성을 좌우한다.** 날짜, 좌표계, 구름 비율, 처리 수준을 알아야 같은 분석을 다시 할 수 있다.
5. **공개 데이터에도 규칙은 남아 있다.** 라이선스, 상업적 이용, 재배포, 개인정보 보호를 확인해야 한다.

## 5. 실제 사례로 먼저 보기

이 장의 실습에서는 Microsoft Planetary Computer의 STAC API를 이용해 서울 지역 Sentinel-2 영상을 찾았다. 실제 실행 로그에 따르면:

- Sentinel 관련 컬렉션은 총 `16개`였다.
- 서울 지역에서 `2024년 6~8월`, `구름 10% 미만` 조건으로 검색한 Sentinel-2 영상은 `5개`였다.
- 이 5개 영상의 평균 구름 비율은 `6.8%`였다.
- 같은 조건으로 Landsat을 검색했을 때는 `6개` 영상이 나왔다.

또 다른 실습에서는 파일 포맷을 비교했다. `50,000개 포인트`, `6개 컬럼` 데이터를 저장하고 읽은 결과는 다음과 같았다.

- GeoJSON 파일 크기: `11.89 MB`, 읽기 시간: `0.712초`
- Shapefile 파일 크기: `21.05 MB`, 읽기 시간: `0.488초`
- GeoParquet 파일 크기: `2.18 MB`, 읽기 시간: `0.052초`

즉 같은 데이터라도 포맷에 따라 저장 공간과 읽기 속도가 크게 달라졌다. 여기서 중요한 것은 숫자를 외우는 것이 아니라, **데이터를 찾는 문제와 데이터를 읽는 문제는 서로 다른 문제**라는 점이다.

여기서 바로 코드를 보는 것보다, 먼저 **사람이 웹 화면에서 어떻게 검색하는가**를 떠올리는 편이 이해가 쉽다. 실제 서비스는 보통 메뉴형 화면으로 검색한다.

- Copernicus Browser는 왼쪽 사이드바에서 위치, 날짜, 데이터셋, 시각화, 다운로드 조건을 고르게 되어 있다.
- Planetary Computer도 `Explorer` 화면에서 지도와 필터를 이용해 데이터셋을 고르고 결과를 시각적으로 확인할 수 있다.

즉 초보자는 보통 다음 순서로 검색한다.

1. 지도에서 서울 근처를 찾는다.
2. Sentinel-2 같은 데이터셋을 고른다.
3. 날짜 범위를 2024년 6월부터 8월까지로 잡는다.
4. 구름이 적은 장면만 남기도록 필터를 건다.

STAC API 코드는 이 과정을 **메뉴 클릭 대신 코드로 반복 가능하게 적어 놓은 것**에 가깝다. 그래서 아래 코드를 볼 때는 문법을 외우기보다, "방금 웹 화면에서 고른 조건을 코드로 옮긴 것"이라고 읽는 편이 맞다. 전체 실행 코드는 `practice/chapter3/code/3-1-stac-search.py`와 `practice/chapter3/code/3-2-cloud-formats.py`에 있다.

```python
from pystac_client import Client

# 1) STAC 카탈로그에 접속한다.
catalog = Client.open(
    "https://planetarycomputer.microsoft.com/api/stac/v1"
)
```

여기까지는 "어느 STAC 서버에 들어갈 것인가"만 정한 상태다. 아직 검색은 하지 않았다.

```python
# 2) 먼저 어떤 컬렉션을 쓸지 정한다.
collection_name = "sentinel-2-l2a"
```

이 한 줄은 웹 화면에서 **데이터셋 메뉴에서 Sentinel-2 Level-2A를 고른 것**에 해당한다. 입문 단계에서는 `collections=[...]`도 결국 **검색 대상 데이터 묶음의 이름을 넣는 자리**라고 이해하면 된다.

```python
# 3) 검색 범위를 따로 적어 둔다.
seoul_bbox = [126.8, 37.4, 127.2, 37.7]
summer_2024 = "2024-06-01/2024-08-31"
cloud_limit = {"eo:cloud_cover": {"lt": 10}}
```

이 세 줄은 각각 다른 역할을 한다.

- `seoul_bbox`: 지도에서 서울 주변 범위를 잡은 것
- `summer_2024`: 날짜 메뉴에서 2024년 여름을 고른 것
- `cloud_limit`: 구름 필터에서 10% 미만만 남기라고 건 것

즉 초보자는 이 코드를 "어려운 쿼리"로 보지 말고, **지역 조건**, **시간 조건**, **품질 조건**을 따로 적어 둔 것이라고 읽는 편이 좋다.

```python
# 4) 이제 위 조건을 한 번에 묶어 검색한다.
search = catalog.search(
    collections=[collection_name],
    bbox=seoul_bbox,
    datetime=summer_2024,
    query=cloud_limit,
    max_items=20,
)

items = list(search.item_collection())
print(len(items))
print(items[0].id)
print(items[0].properties["eo:cloud_cover"])
```

이 짧은 코드에서 읽어야 할 핵심은 세 가지다.

- `Client.open(...)`은 STAC 서버의 루트 Catalog에 접속하는 단계다.
- `catalog.search(...)`는 앞에서 따로 적어 둔 컬렉션, 공간 범위, 날짜, 구름 조건을 한 번에 묶어 실제 장면을 찾는 단계다.
- `items[0]`에 접근하면 첫 번째 검색 결과의 `id`, 구름비율, 날짜, Asset 목록 같은 메타데이터를 읽을 수 있다.

포맷 비교도 같은 방식으로 핵심만 보면 구조가 단순하다.

```python
import geopandas as gpd
import time

# 같은 GeoDataFrame을 서로 다른 형식으로 저장한다.
gdf.to_file("test.geojson", driver="GeoJSON")
gdf.to_file("test.shp")
gdf.to_parquet("test.parquet")

# 다시 읽으면서 시간을 비교한다.
t0 = time.time()
_ = gpd.read_file("test.geojson")
t_geojson = time.time() - t0

t0 = time.time()
_ = gpd.read_file("test.shp")
t_shp = time.time() - t0

t0 = time.time()
_ = gpd.read_parquet("test.parquet")
t_parquet = time.time() - t0
```

이 코드가 보여 주는 질문은 단순하다. **같은 내용이라도 어떤 포맷으로 저장하고 읽느냐에 따라 작업 속도가 얼마나 달라지는가**다. 3장의 실습은 바로 이 차이를 실제 숫자로 확인하는 데 목적이 있다.

이 코드의 출력에서 먼저 볼 것은 다음 세 가지다.

- Sentinel-2 검색 결과가 몇 개인지 본다. 공개 데이터가 많아 보여도 실제 조건을 걸면 남는 장면 수가 많지 않을 수 있다는 점이 드러난다.
- 첫 번째 Item의 `id`와 구름비율을 본다. STAC 검색 결과가 단순 파일 목록이 아니라 메타데이터를 가진 관측 단위라는 점을 보여 준다.
- GeoJSON, Shapefile, GeoParquet의 읽기 시간이 어떻게 다른지 본다. 데이터를 찾는 문제와 데이터를 빠르게 읽는 문제는 별개라는 사실이 출력에서 바로 보인다.
- 네 번째 코드(`3-4-commercial-data-bias.py`)의 출력에서는 두 숫자를 먼저 본다. 서울 여덟 업종을 합친 OSM 포착률 `0.217`, 그리고 데이터 사용 판정에서 "그대로 사용"으로 분류된 행정동 `1개`. 이 둘만 보아도 "지도에 없다"를 "현실에 없다"로 읽으면 안 되는 이유가 드러난다.

## 6. 데이터를 찾는 길: 공개 위성영상과 GIS 데이터셋

### 6.1 어떤 위성 데이터를 먼저 떠올려야 할까

공개 위성영상을 처음 접할 때는 종류가 너무 많아 보인다. 그래서 세 가지만 먼저 구분해도 도움이 된다.

- **Landsat 8/9**
  - 긴 시간축이 강점이다.
  - 1970년대부터 이어지는 관측 계보가 있어 장기 변화 분석에 유리하다.
  - 해상도는 `30m` 수준이라 건물 한 채를 정교하게 보기보다는 토지피복, 식생, 장기 변화에 자주 쓰인다.
- **Sentinel-2**
  - 해상도와 주기의 균형이 좋다.
  - `10m` 해상도와 짧은 재방문 주기 덕분에 도시, 농업, 환경 분석에서 매우 자주 등장한다.
- **MODIS**
  - 넓은 범위를 자주 보는 데 강하다.
  - 해상도는 거칠지만 거의 매일 전 지구를 보는 장점이 있어 기후·대기·대규모 환경 변화에 적합하다.

이 차이는 단순한 스펙 차이가 아니다. 실제 질문을 바꾸는 차이다.

- "몇십 년 동안 숲이 얼마나 변했는가"를 묻는다면 Landsat이 먼저 떠오른다.
- "이번 여름 서울 주변 녹지 상태를 비교하고 싶다"면 Sentinel-2가 더 자연스럽다.
- "동아시아 전체의 대기나 해양 변화를 넓게 보고 싶다"면 MODIS가 떠오른다.

즉 공개 데이터 선택은 "어느 위성이 더 좋나"가 아니라 **어느 질문에 더 맞나**의 문제다.

### 6.2 위성영상만으로는 왜 부족할까

위성영상만 있으면 모든 공간 분석이 될 것처럼 보이지만 실제로는 그렇지 않다. 위성영상은 땅 표면의 상태를 보여 주는 데 강하지만, 정책과 행정은 대개 다른 종류의 데이터와 함께 움직인다.

- **OpenStreetMap**은 도로, 건물, 시설 위치를 붙이는 데 유용하다.
- **Natural Earth**는 국가 경계와 기본 지도를 빠르게 마련하는 데 유용하다.
- **WorldPop** 같은 인구 자료는 "어디에 사람이 많은가"를 연결하는 데 유용하다.

예를 들어 녹지율을 위성영상에서 계산했다고 해도, 실제 질문은 그 다음부터 시작된다.

- 어느 행정동의 녹지 접근성이 낮은가
- 어떤 생활권의 인구 노출이 큰가
- 어느 구역에 예산을 우선 배정해야 하는가

이때는 영상만으로 끝나지 않고 도로, 행정경계, 인구, 시설 데이터가 함께 들어온다. 그래서 3장은 "위성영상만 찾는 법"이 아니라 **GeoAI에 들어오는 데이터 전체의 생태계**를 보는 장이다.

한 가지를 미리 짚어 두자. 이렇게 가져오는 벡터·POI 데이터에는 **빈 구멍**이 있다. 위성영상은 구름만 없으면 그 지역을 빠짐없이 찍지만, 시설 위치 데이터는 누군가 등록해야 생기므로 등록되지 않은 곳이 통째로 빠진다. 그 구멍이 얼마나 크고 어디에 몰리는지는 10절에서 서울 자료로 직접 재 본다.

## 7. STAC: 검색 질서를 실제로 읽어 보기

### 7.1 왜 STAC가 필요했을까

위성데이터는 오랫동안 센서와 기관마다 메타데이터 구조가 달랐다. Landsat은 Landsat 방식대로, Sentinel은 Sentinel 방식대로, 다른 자료는 또 다른 방식대로 설명이 붙어 있었다. 이렇게 되면 연구자나 개발자는 데이터를 분석하기 전에 **찾는 법부터 따로 배워야** 했다.

STAC는 이 문제를 줄이기 위한 표준이다. 쉽게 말해, 서로 다른 위성데이터를 가능한 한 비슷한 방식으로 찾게 하려는 약속이다.

### 7.2 Planetary Computer STAC API를 보고 있다고 가정해 보자

이제 실제 자료를 보고 있다고 생각해 보자.  
https://planetarycomputer.microsoft.com/api/stac/v1

이 주소는 단순한 다운로드 링크가 아니라 **JSON 값을 돌려주는 STAC API 루트 엔드포인트**다. 브라우저에서 열면 사람용 설명 페이지 대신, STAC 서버가 자기 구조를 설명하는 `Catalog` 응답이 먼저 나온다. 실제로는 이런 값들이 보인다.

- `type: "Catalog"`
- `id: "microsoft-pc"`
- `title: "Microsoft Planetary Computer STAC API"`
- `stac_version: "1.0.0"`
- `links: [...]`

즉 이 주소는 "여기서 검색을 시작할 수 있다"는 말만 하는 것이 아니라, **이 서버가 어떤 종류의 STAC 서버인지, 다음에 어디로 가야 하는지까지 JSON으로 알려 주는 시작값**이다.

여기서 특히 중요한 것은 `links`다. 이 배열 안에 다음 진입점이 들어 있다.

- `collections`: 어떤 데이터 묶음들이 있는지 보여 주는 목록
- `search`: 조건을 넣어 실제 장면을 찾는 검색 API
- `docs`: 사람이 읽기 쉬운 문서 페이지

STAC에서 가장 바깥쪽 구조를 보통 **Catalog**라고 부른다. Catalog는 "여기에서 여러 종류의 컬렉션을 찾을 수 있다"는 시작점에 가깝다.

여기서 학생이 꼭 구분해야 할 점이 있다. 실제 사용 흐름에는 두 층이 있다.

- **브라우저 층**: 지도와 메뉴를 보고 사람이 직접 고른다.
- **API 층**: 방금 고른 조건을 코드로 보내 같은 검색을 반복한다.

예를 들어 Copernicus Browser에서 서울, Sentinel-2, 2024년 여름, 낮은 구름량을 클릭해 찾는 과정은, STAC API 코드에서는 `bbox`, `collections`, `datetime`, `cloud_cover` 조건으로 바뀐다. 즉 API는 브라우저와 경쟁하는 방식이 아니라, **브라우저에서 하던 검색을 자동화하는 방식**에 더 가깝다.

실제 로그에서 이 Catalog 아래 Sentinel 관련 컬렉션을 찾았더니 `16개`가 나왔다. 이 말은 Sentinel이라는 이름이 붙은 자료가 하나만 있는 것이 아니라, Sentinel-1, Sentinel-2, Sentinel-3, Sentinel-5P처럼 여러 종류가 있으며, 그 안에서도 용도와 처리 수준이 나뉜다는 뜻이다.

### 7.3 Collection, Item, Asset를 실제 예로 읽기

실습에서는 `sentinel-2-l2a` 컬렉션을 사용했다. 여기서 `Collection`은 같은 종류의 데이터 묶음이라고 생각하면 된다. 도서관 비유를 쓰면 한 서가와 비슷하다.

그 안에서 검색 결과 하나를 실제로 보면 다음 정보가 나왔다.

- Item ID: `S2B_MSIL2A_20240829T021539_R003_T52SCG_20240829T043313`
- 날짜: `2024-08-29 02:15:39`
- 구름비율: `8.1%`
- Asset 수: `23개`

이제 이 한 줄씩을 해석해 보자.

- **Item**은 한 시점, 한 장면의 개별 관측이다.
- `2024-08-29`라는 날짜는 "언제 찍힌 장면인가"를 알려 준다.
- `8.1%`라는 구름비율은 "쓸 만한 장면인가"를 판단할 단서가 된다.
- Asset이 `23개`라는 말은 이 장면에 실제로 연결된 파일이 여러 개라는 뜻이다.

여기서 `Asset`은 실제 파일이다. 로그에 나온 Asset 일부는 다음과 같았다.

- `B02`
- `B03`
- `B04`
- `B08`
- `SCL`
- `visual`

이 파일 이름을 보고 무엇을 읽어야 하는지도 감이 잡혀야 한다.

- `B02`, `B03`, `B04`는 밴드 파일이다.
- `B08`은 근적외선 관련 분석에서 자주 중요하다.
- `SCL`은 장면 분류와 품질 확인에 도움을 주는 파일이다.
- `visual`은 사람이 빠르게 보기 좋은 미리보기 성격의 파일이다.

즉 STAC를 이해한다는 것은 추상 구조를 외우는 것이 아니라, **실제 Item 한 개를 보고 "이 장면은 언제 찍혔고, 상태는 어떻고, 어떤 파일을 읽으면 되는가"를 해석할 수 있는 상태**에 가까워지는 것이다.

### 7.4 서울 여름철 검색 결과가 의미하는 것

실습에서는 서울 지역을 `2024년 6~8월`, `구름 10% 미만`으로 검색했다. 그 결과 Sentinel-2 영상은 `5개`였다.

이 숫자는 단순히 "5개 찾았다"로 끝나지 않는다. 한국의 여름은 장마와 구름이 많기 때문에, 조건을 까다롭게 잡으면 쓸 수 있는 장면 수가 생각보다 적어진다는 뜻이다.

실제 평균 구름 비율은 `6.8%`였고, `5% 미만` 장면은 `1개`뿐이었다. 이것은 초심자에게 아주 중요한 감각을 준다. 공개 데이터는 많아 보여도, **내 지역, 내 시기, 내 품질 조건을 동시에 만족하는 자료는 생각보다 적을 수 있다.**

그래서 실무에서는 다음 같은 판단이 따라온다.

- 조건을 조금 완화할까
- 다른 시기를 넓혀 볼까
- Sentinel-1 SAR 같은 대안을 쓸까

이 장면에서 이미 2장과 3장이 연결된다. 2장은 구름과 전처리를 배웠고, 3장은 그 때문에 검색 결과 자체가 달라진다는 점을 보여 준다.

## 8. 데이터를 읽는 길: 포맷은 왜 중요한가

### 8.1 파일을 받았다고 끝난 것이 아니다

데이터를 찾았다고 해서 바로 편해지는 것은 아니다. 이번에는 **읽는 방식**이 문제다. 데이터가 너무 크면, 저장과 읽기 속도 자체가 작업의 병목이 된다.

예전에는 파일을 통째로 내려받는 방식이 더 자연스러웠다. 하지만 GeoAI에서는 한 장의 위성영상이나 대규모 벡터 데이터가 너무 크기 때문에, 전체를 항상 다 복사하는 방식이 비효율적이다.

그래서 클라우드 네이티브 포맷이 중요해진다. 핵심 생각은 하나다. **필요한 부분만 읽자.**

### 8.2 실제 숫자로 보는 포맷 차이

실습에서는 `50,000개 포인트`, `6개 컬럼` 데이터를 세 가지 형식으로 저장하고 읽었다.

- GeoJSON: `11.89 MB`, 읽기 `0.712초`
- Shapefile: `21.05 MB`, 읽기 `0.488초`
- GeoParquet: `2.18 MB`, 읽기 `0.052초`

여기서 가장 먼저 보이는 것은 파일 크기 차이다. GeoParquet는 같은 내용을 담고도 훨씬 작았다. 읽기 속도도 빨랐다. GeoJSON보다 `13.6배` 빨랐다.

이 숫자는 "GeoParquet가 더 현대적이다" 같은 취향의 문제가 아니라, 실제 작업에서 체감하는 시간을 바꾸는 숫자다. 데이터가 더 커질수록 차이는 더 크게 느껴진다.

### 8.3 COG, Zarr, GeoParquet를 각각 어떻게 이해할까

이 세 용어는 처음 보면 모두 낯설다. 하지만 역할을 한 줄로 정리하면 훨씬 단순하다. 파일을 실제로 받았을 때 확장자가 무엇으로 보이는지도 함께 알아 두면, 나중에 폴더에서 파일을 마주쳤을 때 바로 알아볼 수 있다.

- **COG**: 큰 위성영상에서 필요한 부분만 읽기 좋게 만든 래스터 포맷. 확장자는 `.tif`나 `.tiff`로, 겉보기에는 일반 GeoTIFF와 똑같다. 다른 점은 파일 안쪽 구조뿐이라, 어떤 `.tif`가 진짜 COG인지는 전용 도구로 확인해야 한다.
- **Zarr**: 시계열과 다차원 배열을 나눠 읽기 좋게 만든 포맷. 파일 하나가 아니라 `data.zarr`라는 **폴더** 형태로 나타난다. 그 안에 조각(청크)마다 별도 파일이 들어 있다. 전송할 때는 이 폴더를 통째로 압축한 `.zarr.zip`을 쓰기도 한다.
- **GeoParquet**: 큰 벡터 데이터를 빠르고 작게 다루기 좋게 만든 포맷. 확장자는 `.parquet`다.

비교를 위해 3장 실습에서 함께 쓴 벡터 포맷의 확장자도 짚어 두면, GeoJSON은 `.geojson`, Shapefile은 `.shp` 한 개가 아니라 `.shp`·`.shx`·`.dbf` 같은 파일 여러 개가 세트로 붙어 다닌다.

여기서 중요한 공통점은 모두 **필요한 부분만 효율적으로 다루려는 방향**이라는 점이다.

책 비유를 쓰면:

- GeoJSON은 내용을 긴 글로 다 풀어 쓴 복사본에 가깝다.
- GeoParquet는 정리된 표와 색인을 붙여, 필요한 부분을 빨리 꺼내 보기 좋게 만든 책에 가깝다.

### 8.4 메타데이터는 왜 같이 봐야 할까

포맷이 빠르다고 해서 충분한 것은 아니다. 다음 정보가 빠지면 분석은 다시 흐려진다.

- 언제 관측했는가
- 어디를 덮는가
- 어떤 좌표계를 쓰는가
- 구름이 얼마나 있는가
- 처리 수준이 어느 정도인가

이런 정보가 바로 메타데이터다. 메타데이터가 없으면 같은 파일을 다시 보더라도 해석이 달라질 수 있다. 반대로 메타데이터가 잘 붙어 있으면, 몇 달 뒤에 다시 봐도 "이 자료가 어떤 상태의 데이터였는가"를 따라갈 수 있다.

즉 좋은 포맷은 단순히 빠른 포맷이 아니라, **읽기 성능과 설명 정보가 함께 붙어 있는 포맷**에 가깝다.

### 8.5 정말 필요한 부분만 받으면 얼마나 아낄까

앞에서 "COG는 필요한 부분만 읽는다"고 여러 번 말했다. 그런데 이 말이 실제로 얼마나 차이를 만드는지 숫자로 보지 않으면 그냥 구호로 끝나기 쉽다. 그래서 실습에서는 서울 지역 Sentinel-2 영상 하나를 놓고, "전체 파일"과 "강남 소구역만"을 직접 비교했다.

- 원본 COG 파일(밴드 하나, 10m 해상도) 전체 크기: `268.5 MB`, 전체 픽셀 수는 `120,560,400개`(약 1억 2천만 개)다.
- 실제로 받은 것은 강남 일대 약 2km×2km 구역, `58,320개` 픽셀뿐이다. 전체의 `0.048%`에 불과하다.
- 이 작은 구역을 받는 데 걸린 시간은 `1.60초`였다.
- 받은 구역은 `gangnam_b04_window.tif`라는 91.0 KB짜리 작은 파일로 저장했다. 268.5MB 원본은 이 과정에서 단 한 번도 컴퓨터에 통째로 저장되지 않았다.

책 비유로 다시 보면, 268.5MB짜리 책 한 권을 통째로 복사하지 않고 필요한 두세 페이지(강남 부분)만 뜯어서 받은 셈이다. 책이 아무리 두꺼워도 원하는 페이지 몇 장을 받는 데 걸리는 시간은 크게 늘어나지 않는다. 이것이 "다운로드 없이 필요한 부분만 읽는다"는 말의 실제 크기다.

한 가지는 정확히 짚고 넘어가야 한다. `0.048%`는 **픽셀 개수**로 정확히 계산한 값이지만, 실제로 오간 데이터양(바이트)이 정확히 이 비율만큼 작다는 뜻은 아니다. COG는 256~512픽셀 크기의 작은 사각형(내부 타일) 단위로 압축되어 있어서, 원하는 영역이 타일 경계에 걸치면 타일 몇 개를 통째로 더 받게 된다. 그래도 268.5MB를 다 받는 것과는 비교할 수 없을 정도로 적은 양이라는 방향은 변하지 않는다.

## 9. 데이터를 쓰는 길: 거버넌스와 라이선스

### 9.1 공개 데이터는 자유이용과 같은 말이 아니다

공개 데이터라는 말을 처음 들으면 "그러면 그냥 써도 되는 것 아닌가?"라고 생각하기 쉽다. 하지만 실제로는 그렇지 않다. 공개되어 있다는 것과 **아무 제약 없이 마음대로 쓸 수 있다**는 것은 다른 말이다.

실제 포털과 데이터 제공처의 이용 규칙을 하나씩 살펴보면, 대표적인 공개 데이터도 서로 다른 규칙을 갖고 있다.

- **Natural Earth**는 제약이 매우 적은 편이다.
- **OpenStreetMap**은 ODbL 규칙을 함께 봐야 한다.
- **한국 공공데이터**는 공공누리 유형에 따라 상업적 이용과 변경 가능 여부가 달라진다.

따라서 프로젝트 초반에 물어야 할 질문은 단순하다.

- 출처 표기가 필요한가
- 수정해도 되는가
- 상업적으로 써도 되는가
- 다시 배포해도 되는가

이 질문을 나중에 하면 늦는다. 데이터를 다 모으고 분석까지 한 뒤에 막히는 경우가 실제로 많다.

### 9.2 국내 포털은 각각 무엇을 기대하고 들어가야 할까

이제 실제 포털을 보고 있다고 가정해 보자.

- **국가공간정보포털**  
  국토와 공간정보 중심의 인프라다. 행정경계, 지적, 건물통합정보 같은 공간 레이어를 기대하게 된다.
- **공공데이터포털**  
  부처와 지자체 전반의 공개데이터 창구다. 공간정보뿐 아니라 행정, 환경, 교통, 복지 자료도 함께 만난다.
- **SGIS 통계지리정보서비스**  
  통계격자, 집계구, 인구와 가구 같은 공간 통계를 기대하게 된다. 정책 분석에서 매우 자주 만난다.
- **브이월드**  
  배경지도와 시각화, API 활용에 더 가까운 역할을 한다.

즉 같은 "공공 포털"이라도 들어가는 목적이 다르다. 이런 차이를 모르면 자료를 찾는 시간만 오래 걸리고, 어떤 포털에 무엇을 기대해야 하는지 감이 잡히지 않는다.

### 9.3 왜 개인정보와 공개 범위를 같이 생각해야 할까

공간데이터는 해상도가 높아질수록 위험도 같이 커진다.

- 건물 단위 데이터
- 미세 격자 데이터
- 이동 경로 데이터

이런 자료는 분석 자체보다 **공개 결과물의 형태**가 더 민감할 수 있다. 특정 개인이나 가구가 직접 드러나지 않더라도, 다른 정보와 결합되면 다시 식별될 위험이 생길 수 있기 때문이다.

그래서 어떤 데이터는 분석에는 쓸 수 있어도, 공개 보고서나 앱 화면에는 다른 형태로 바꿔서 보여 줘야 한다. 이것이 거버넌스가 중요한 이유다. 거버넌스는 추상적인 법 설명이 아니라, **무엇을 어디까지 보여 줄 수 있는가**를 정하는 현실 문제다.

## 10. 데이터에 없는 것과 현실에 없는 것

### 10.1 우리 동네 그 가게는 왜 지도에 없을까

지도 앱에서 우리 동네를 검색해 보면, 분명히 있는 가게인데 안 나오는 경우가 있다. 그 가게가 없어진 게 아니다. **아무도 지도에 올리지 않은 것뿐이다.**

여기까지는 그냥 불편한 일이다. 문제는 이 데이터를 가지고 판단을 내릴 때 생긴다. 어떤 동네에 카페가 두 곳만 잡힌다고 하자. 읽는 방법이 둘이다.

1. 정말 두 곳뿐이다 → 이 동네는 **빈 시장**이다. 창업하기 좋다.
2. 두 곳만 등록되었다 → 실제로는 스무 곳이다. 이미 **포화 상태**다.

정반대 결론인데, 데이터만 보면 둘을 구분할 방법이 없다. 그러니 데이터 하나만 놓고 "여기가 비었다"고 말하면 안 된다.

### 10.2 그러면 어떻게 확인할까

같은 것을 다른 방식으로 센 자료를 하나 더 구하면 된다.

- **공공기관이 조사해 만드는 점포 목록**은 기관이 나서서 채운다. 소상공인시장진흥공단이 분기마다 공개하는 상가(상권)정보가 그것이다. 그래서 상대적으로 빠짐이 적다.
- **지도 데이터(OpenStreetMap)**는 누군가 자원해서 올려야 생긴다. 그래서 빠질 수 있다.

둘을 나눠 보면 "얼마나 빠졌는가"가 숫자로 나온다. 이 비율을 **포착률**이라고 부른다.

포착률 = 지도에 있는 점포 수 ÷ 기준 자료에 있는 점포 수

1에 가까우면 거의 다 담긴 것이고, 0.1이면 열에 아홉을 놓친 것이다.

한 가지는 정확히 해 두자. 기준으로 삼는 자료도 **완벽하지 않다.** 문 닫은 가게가 아직 목록에 남아 있을 수 있고, 등록하지 않고 장사하는 곳은 애초에 없다. 그래서 이것을 "정답"이 아니라 **"지금 구할 수 있는 가장 나은 기준"**이라고 부른다. 이 차이는 뒤에서 실제로 문제를 일으킨다.

### 10.3 서울에서 직접 재 보면

실습에서는 서울 전체를 대상으로 세 자료를 맞대어 보았다. 소상공인시장진흥공단이 공개하는 점포 목록(서울 `554,092개`), OpenStreetMap의 POI, 그리고 서울시가 공개하는 카드 기반 추정매출이다. 결과는 이랬다.

- 여덟 업종을 합친 OSM 포착률은 `0.217`이었다. 서울에서도 **다섯 곳 중 한 곳 남짓만 지도에 있다.**
- 업종에 따라 크게 갈렸다. 편의점 `0.713`, 카페 `0.178`, 화장품 `0.039`. 편의점은 브랜드가 몇 개로 정해져 있고 간판이 눈에 띄어 올리기 쉽다. 화장품 가게는 그렇지 않다.
- 동네에 따라서도 갈렸다. 가장 높은 곳은 가회동(`1.07`), 가장 낮은 곳은 상계8동(`0.00`)이었다. 서울시청에서 멀어질수록 포착률이 떨어지는 경향이 통계적으로 뚜렷했다.

여기서 이상한 값이 하나 나왔다. **미용실은 포착률이 `1.249`, 곧 1을 넘었다.** 실제보다 더 많이 담겼다는 뜻인데, 있을 수 없는 일이다. 원인을 찾아보니 OSM에서 미용실을 뜻하는 태그(`shop=hairdresser`)에 네일숍과 피부관리실까지 함께 들어가 있었다. 세는 대상이 서로 달랐던 것이다. 상권정보 쪽도 네일숍·피부관리실까지 넓혀서 다시 세니 `0.757`로 떨어졌다.

**이것이 이 절에서 가장 중요한 교훈이다.** 두 자료를 비교할 때는 "같은 것을 세고 있는가"를 먼저 확인해야 한다. 확인하지 않으면 1을 넘는 비율 같은 명백한 신호가 나와야 겨우 알아차린다.

### 10.4 카드 자료에는 또 다른 구멍이 있다

서울시가 공개하는 상권 매출 자료는 **카드 결제 기록**을 바탕으로 만든다. 그러니 현금으로 산 것은 담기지 않는다.

그리고 이 자료에는 아예 빈칸도 많다. 점포가 실제로 있는 칸 `10,186개` 중 `1,895개`(`18.6%`)에 매출 기록이 없었다. 어떤 칸이 비는지 보니 규칙이 있었다. **점포가 몇 개 없는 업종일수록 빈다.** 미곡판매는 한 동네에 평균 1.7개뿐인데 결측률이 `0.443`, 한식음식점은 평균 116.5개인데 결측률이 `0.005`다.

빈칸이 아무 데나 생기는 게 아니라 **작은 업종에 몰린다**는 뜻이다. 이걸 모르고 "우리 동네에는 쌀가게가 없네"라고 읽으면 틀린다.

### 10.5 그래서 쓰지 말라는 건가

아니다. **어디까지 믿을지 정해 두고 쓰라**는 것이다.

실습에서는 계산을 하나 해 보았다. 포착률이 0.074인 서점 자료에서, 지도에 한 곳도 없는 동네가 **정말로 비어 있을 확률**은 얼마인가? 답은 `0.156`이었다. 여섯 곳 중 다섯 곳은 서점이 있는데 지도에 없을 뿐이다. 이 확률이 0.80은 되어야 마음 놓고 창업 결정을 내릴 텐데, 그러려면 포착률이 `0.85`는 되어야 한다. 실측은 그 열 배 아래다.

그래서 실습은 서울의 행정동을 세 등급으로 나눴다.

- **그대로 사용**: 포착률이 높아 "없다"를 믿어도 되는 동네 → `1개`
- **보정 후 사용**: 낮지만 얼마나 낮은지 예측되는 동네. 지도에 3개 보이고 예상 포착률이 0.20이면 실제는 15개쯤으로 놓고 판단한다 → `249개`
- **사용 금지**: 낮은 데다 예측도 빗나가는 동네. 여기서는 지도만 보고 판정하지 않고 다른 자료를 찾거나 직접 가 본다 → `159개`

서울에서조차 "그대로 믿어도 되는" 동네가 한 곳뿐이라는 사실이 이 절의 결론이다.

### 10.6 컷라인은 데이터가 정하지 않는다

위에서 "확률이 0.80은 되어야 한다"고 했는데, 이 0.80은 어디서 왔을까? 데이터에서 나온 숫자가 아니다. **틀렸을 때 얼마나 손해인지**에서 나왔다.

- **창업**: 이미 가게가 있는데 없다고 보고 들어가면 인테리어·권리금을 날린다. 손해가 크다. 그래서 확신이 아주 높을 때만 들어간다 → 컷라인 `0.80`
- **공공**: 복지시설이 없는 동네를 놓치면 주민이 계속 불편을 겪는다. 헛짚어서 한 번 더 확인하는 비용은 그보다 훨씬 싸다. 그래서 의심되면 확인하러 간다 → 컷라인 `0.20`

**같은 데이터, 같은 확률인데 결론이 반대다.** 무엇을 더 두려워하느냐가 갈랐다. 데이터 분석에서 숫자는 재료일 뿐이고, 어디서 자를지는 사람이 정한다.

## 13. 과제

이번 장의 과제는 **직접 돌려 보고, 그 결과로 판단하는 것**이다. 명령 한 줄이면 제출할 파일이 만들어진다.

```bash
python scripts/submit.py 3 --id 학번 --name 이름
```

이 명령이 대신 해 준다 — 실습에 필요한 데이터를 먼저 만들고, 대표 실습 `3-4-commercial-data-bias.py`을 돌리고, 제출용 파일 하나를 만든다. 저장소를 내려받아도 데이터 파일은 들어 있지 않으므로 첫 단계가 꼭 필요하다. 그래서 처음 돌리는 장은 조금 더 걸린다.

끝나면 `submissions/` 폴더에 `제출_3장_학번.md` 파일이 생긴다. 열어 보면 실행 결과가 이미 붙어 있다. **눈여겨볼 곳은 업종별·동별 포착률, 그리고 1을 넘는 값이 있는지.**

맨 아래 빈칸 세 개만 채우면 된다.

1. 눈에 띈 숫자 하나를 그대로 옮겨 적고, 왜 눈에 띄었는지 한 문장으로
2. 그 숫자가 왜 그렇게 나왔는가
3. **지도에 점포가 하나도 없는 동네가 있다. '여기는 비어 있으니 창업하자'고 말해도 되는가? 근거를 숫자로 대라.**

**3번이 이 과제의 핵심이다.** 1·2번은 결과를 들여다보면 답이 나오지만 3번은 그렇지 않다. 이 수업이 묻는 것은 숫자를 뽑는 능력이 아니라 그 숫자로 무엇을 정할지 판단하는 능력이다.

채운 파일 **하나만** 올리면 제출이 끝난다.

> **막혀도 제출한다.** 실행이 도중에 실패하면 오류 메시지가 그 파일에 자동으로 담기고, 질문이 "어디서 막혔나"로 바뀐다. 어디서 왜 막혔는지 적은 제출도 온전한 제출이다. 실행 성공 여부로 점수를 매기지 않는다.

> **이 장은 난수를 쓰지 않는다.** 그래서 교재에 적힌 값이 그대로 나와야 정상이고, 옆 사람 결과와도 같다. 다르게 나왔다면 그것이 곧 신호다 — 무엇이 다른지 찾는 것까지가 과제다.

  COG(https://cogeo.org), Zarr(https://zarr.dev), GeoParquet(https://geoparquet.org)의 공식 페이지는 각 포맷이 "필요한 부분만 읽기"를 실제로 어떻게 구현하는지 설명한다.
- **공개 데이터 라이선스 원문**  
  OpenStreetMap이 쓰는 ODbL 원문(https://opendatacommons.org/licenses/odbl/)과 한국 공공누리(https://www.kogl.or.kr)에서 유형별 이용 조건을 직접 확인할 수 있다.
- **개인정보와 공간 데이터**  
  개인정보보호위원회(https://www.pipc.go.kr)에서 개인정보보호법과 가명처리 관련 안내 자료를 볼 수 있다. 위치·이동 데이터처럼 결합 시 재식별 위험이 있는 자료를 다룰 때 출발점이 된다.
- **우리 동네 점포 목록을 직접 보기**  
  소상공인시장진흥공단 상가(상권)정보(https://www.data.go.kr/data/15083033/fileData.do)는 전국 점포를 좌표와 업종까지 붙여 분기마다 공개한다. 로그인 없이 받을 수 있으니, 자기 동네 파일을 열어 실제로 몇 곳이 등록되어 있는지 세어 보면 10절의 포착률 이야기가 훨씬 실감난다.
- **서울 상권을 숫자로 보기**  
  서울시 상권분석 서비스(https://golmok.seoul.go.kr)는 행정동·업종별 추정 매출과 유동인구를 지도 위에서 보여 준다. 이 매출이 카드 결제 자료에서 나온다는 점을 알고 보면, 어떤 업종의 숫자를 더 조심해서 읽어야 하는지 감이 잡힌다.
