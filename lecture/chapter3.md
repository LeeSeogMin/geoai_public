## 2. 지도에 카페가 두 곳뿐인 동네

○ 어느 행정동의 카페가 지도 자료에 두 곳으로 집계됨

□ 이 관측을 읽는 방법은 둘

1. 실제로 두 곳뿐임 → 그 동은 미충족 시장이므로 출점 후보가 됨
2. 더 있지만 등록되지 않았음 → 후보지로 선정하면 이미 포화된 상권에 진입하는 결정이 됨

□ 지도만 확인해서는 두 경우를 구분할 수 없음 — 어느 쪽이든 화면에는 점 두 개가 표시되어 있을 뿐임  
 ○ 공공에서도 같은 오류가 반대 방향으로 발생함 — 자료의 공백을 서비스의 공백으로 읽으면 이미 시설이 있는 지역에 예산이 배정됨

□ 구분하려면 **같은 대상을 다른 방식으로 집계한 추가 자료**가 필요하고, 두 자료를 대조해 얻는 값이 이 장 후반의 **포착률**(coverage rate)임  
 ○ 이 장은 이 문제를 실제 서울 데이터로 분석함 — 자료를 찾아 확보하고(4~5절), 그 자료가 현실을 얼마나 담았는지 측정하고(6~7절), 그 결과로 결정을 내려도 되는지 판정함(8절)

## 4. 카탈로그 검색: STAC

### 4.1 왜 공통 규격이 필요한가

□ 위성영상 메타데이터는 센서마다 형식이 달랐음 — Landsat은 MTL 텍스트, Sentinel-2는 XML, MODIS는 HDF 내부 속성  
 ○ 같은 조건("구름 10% 미만, 이 사각형 안, 이 기간")을 센서마다 다르게 표현하고 별도 파싱 코드를 작성해야 했음

○ **STAC**(SpatioTemporal Asset Catalog)는 이 문제를 해결하기 위한 개방형 표준임. 네 객체가 위에서 아래로 포함 관계를 이룸

| 객체       | 역할                                 | 예시                    |
| ---------- | ------------------------------------ | ----------------------- |
| Catalog    | 최상위 컨테이너                      | Planetary Computer 전체 |
| Collection | 같은 유형 Item의 그룹                | `sentinel-2-l2a`        |
| Item       | 개별 관측 단위(한 장면의 메타데이터) | 특정 날짜·타일의 장면   |
| **Asset**  | Item이 가리키는 실제 파일            | `B04.tif`, `SCL.tif`    |

○ Item은 영상 파일이 아니라 **같은 장면에 속한 파일들을 묶는 색인**임 — 관측 시각, 구름 비율, 공간 범위를 기록하고 실제 파일은 Asset으로 가리킴  
○ Catalog의 API 주소(https://planetarycomputer.microsoft.com/api/stac/v1)를 브라우저에 입력하면 JSON 응답이 표시됨 — Catalog가 실제로 무엇을 담는지 확인할 수 있음

### 4.2 검색 절차와 실제 결과

□ 먼저 실행함. 이 절의 숫자는 전부 이 명령의 출력임

```bash
python lecture_practice/chapter3/code/3-1-stac-search.py
```

□ 코드는 여섯 단계를 순서대로 수행함

1. **엔드포인트 접속** — Catalog API에 접속하여 Collection 목록을 수신함
2. **Collection 선택** — 처리 수준을 정함. `sentinel-2-l1c`는 대기 상단 반사율, `sentinel-2-l2a`는 대기보정을 마친 지표 반사율. 지표 상태를 분석하려면 L2A를 선택함
3. **조건 설정** — bbox(관심 지역을 감싸는 사각형의 서·남·동·북 좌표 네 개), datetime(기간), query(품질 조건)를 지정함
4. **Item 목록 수신** — 조건에 맞는 장면의 메타데이터를 받음
5. **Asset URL 획득** — 필요한 밴드 파일의 주소를 추출함
6. **검색 조건과 Item ID 기록** — 엔드포인트, Collection, bbox, 기간, 품질 조건, 반환 Item ID를 전부 남김

○ 아래는 그 코드에 실제 실행 결과를 주석으로 첨부한 것임

```python
# 주석으로 첨부한 출력의 출처: lecture_practice/chapter3/results/3-1-stac-search.log
from pystac_client import Client

# [1] 엔드포인트 접속 — 인증 없이 검색만 수행함
catalog = Client.open("https://planetarycomputer.microsoft.com/api/stac/v1")

for collection in catalog.get_collections():
    if "sentinel" in collection.id.lower():
        print(collection.id, collection.title)
# 출력: sentinel-1-rtc: Sentinel 1 Radiometrically Terrain Corrected (RTC)
#       sentinel-2-l2a: Sentinel-2 Level-2A
#       ... 총 16개 Sentinel 컬렉션 발견

# [2]~[3] Collection 선택과 조건 설정
search = catalog.search(
    collections=["sentinel-2-l2a"],           # 대기보정을 마친 지표 반사율
    bbox=[126.8, 37.4, 127.2, 37.7],          # 서울 일대(서·남·동·북)
    datetime="2024-06-01/2024-08-31",
    query={"eo:cloud_cover": {"lt": 10}},     # 구름 10% 미만
)

# [4] Item 목록 수신
items = list(search.item_collection())
for i, item in enumerate(items):
    print(i + 1, item.datetime, item.properties["eo:cloud_cover"])
# 출력: 검색 결과: 5개 영상
#       [1] 2024-08-29 02:15 | 구름: 8.1% | 플랫폼: Sentinel-2B
#       [2] 2024-08-29 02:15 | 구름: 0.0% | 플랫폼: Sentinel-2B
#       [3] 2024-08-19 02:15 | 구름: 9.9% | 플랫폼: Sentinel-2B
#       [4] 2024-08-14 02:16 | 구름: 7.0% | 플랫폼: Sentinel-2A
#       [5] 2024-08-04 02:15 | 구름: 9.0% | 플랫폼: Sentinel-2A
#       평균 구름 비율: 6.8% | 구름 5% 미만: 1개

# [5] Asset URL 획득 — 적색 밴드(B04) 파일 주소
item = items[0]
href = item.assets["B04"].href
# 출력: ID: S2B_MSIL2A_20240829T021539_R003_T52SCG_20240829T043313
#       좌표계: EPSG:32652 | 구름비율: 8.1%
#       Asset 목록 (23개): AOT B01 B02 B03 B04 ... SCL WVP visual
```

○ `results/3-1-stac-search.log`는 코드 마지막 줄의 문구를 고치기 전에 저장한 실행 기록임 — 개수·구름 비율 등 숫자는 지금 코드와 같고 마지막 한 줄의 표현만 다름

□ 화면에 나온 값에서 읽을 것  
 ○ 여름 석 달 동안 구름 10% 미만인 장면은 5개이고, 그중 5% 미만인 장면은 1개임 — 한국 여름은 장마·태풍 때문에 맑은 장면이 드묾  
 ○ 같은 날짜(2024-08-29)의 Item이 두 개 나타남. 서울이 두 Sentinel-2 타일 경계에 걸쳐 있어 타일마다 별도 Item이 생성되기 때문이며, 관심 영역이 타일 경계에 걸리면 한 시점에도 Item 두 개를 결합해야 함  
 ○ Item 하나가 Asset을 23개 포함함 — 밴드별 `.tif`와 메타데이터 XML이 함께 포함되어 있고, 적색 밴드가 필요하면 `item.assets["B04"].href`에서 해당 파일 주소를 추출함  
 ○ 6단계는 코드가 자동으로 수행하지 않음. 엔드포인트·Collection·bbox·기간·구름 조건과 반환된 Item ID를 직접 기록해야 함

□ 코드는 마지막에 같은 조건으로 Landsat C2 L2도 검색함 — 결과는 `6`개(구름 3.1 / 6.9 / 8.2%)로 Sentinel-2의 5개보다 많음  
 ○ 재방문 주기만 보면 Sentinel-2가 5일, Landsat이 16일이므로 Sentinel-2가 더 많은 장면을 제공해야 하지만, 검색 개수는 관측 횟수가 아니라 조건을 통과한 장면의 수로 결정됨  
 ○ 구름 10% 미만 조건이 여름 장면 대부분을 제외하므로 주기가 짧다는 사실이 검색 개수로 그대로 이어지지 않음. `max_items=20`도 반환 개수에 상한을 두지만 이번 실행은 5개·6개여서 상한에 도달하지 않았음 — **사양에 적힌 주기가 아니라 실행이 반환한 개수를 해석의 근거로 삼음**

> - **라이브 카탈로그 조회는 재현되지 않음**
> - 아카이브가 갱신되거나 장면이 재처리되면 같은 조건에서도 반환 개수가 달라짐
> - 실행했을 때 5개가 아니어도 정상이며, 그래서 6단계의 기록이 필수임 — 보고서에는 "5개가 검색되었다"가 아니라 실제로 쓴 Item ID 목록을 실음

## 5. 부분 읽기: 필요한 조각만 받는다

### 5.1 원리

○ 4절에서 얻은 Asset URL은 클라우드에 저장된 파일을 가리킴 — Sentinel-2 한 밴드가 수백 MB인데, 실제로 필요한 것은 관심 영역의 일부 픽셀뿐임

□ 전통 포맷(GeoTIFF·Shapefile 등)은 파일을 처음부터 순서대로 읽는 방식을 가정함 — 10GB 영상에서 100×100 픽셀만 필요해도 전체를 받아야 했음  
 ○ **HTTP Range Request**는 이 전제를 바꿈 — "이 파일의 몇 번째 바이트부터 몇 번째까지만 보내 달라"고 요청하는 HTTP 기능

□ 부분 읽기는 세 단계로 진행함

1. 파일 앞부분의 **헤더**만 받아 내부 구조(전체 해상도, 타일 크기, 각 타일의 바이트 위치)를 읽음 — 이 단계에서 픽셀 본문은 전송되지 않음
   ○ 헤더를 개념적으로 표현하면 다음과 같음. 실제 COG 헤더의 바이너리 구조를 단순화한 가상 예시임

   ```json
   {
     "width": 10000,
     "height": 8000,
     "tile_width": 256,
     "tile_height": 256,
     "tiles": {
       "row=12,col=34": { "offset": 1843200, "length": 52781 },
       "row=12,col=35": { "offset": 1895981, "length": 49120 }
     }
   }
   ```

   ○ 이 예시에서 영상 전체 크기는 10,000×8,000 픽셀이고, 한 타일은 256×256 픽셀임. `row=12,col=34` 타일은 파일의 1,843,200번째 바이트부터 52,781바이트를 차지하므로, 해당 구간만 요청할 수 있음

### 6.1 기준 자료를 정한다

□ 포착률은 나눗셈이므로 분모가 될 자료가 필요함. 이 자료를 **준모집단 기준**(reference frame)이라 함 — 현실의 참값이 아니라, 다른 자료의 누락 정도를 비교하기 위한 기준 자료  
 ○ 모든 점포를 누락 없이 담은 단일 자료는 없음. 어떤 자료를 사용해도 폐업 반영 지연, 무등록 영업, 업종 분류 차이, 위치 오류가 남을 수 있음  
 ○ 이 사례에서는 상가정보를 기준으로 삼음 — 소상공인시장진흥공단이 영업 중인 상가업소의 상호·업종·주소·경도·위도 등을 제공하므로, OSM과 점포 단위로 비교할 공개 기준 자료로 선택함 ([공공데이터포털 상가(상권)정보](https://www.data.go.kr/dataset/15012005/openapi.do?lang=ko))  
 ○ 통계청의 전국사업체조사도 공식 기준 자료이지만, 공개 자료는 주로 지역·업종별 집계 통계이며 개별 점포의 좌표 목록과는 다름 ([2024년 전국사업체조사 결과](https://www.kostat.go.kr/board.es?act=view&bid=233&list_no=438719&mid=a10301090300&nPage=1&ref_bid=&tag=))  
 ○ 상가정보도 모집단은 아님 — 폐업 신고가 늦으면 이미 닫은 점포가 남고, 무허가 영업은 처음부터 없음

```text
포착률 = OSM에서 확인된 카페 수
       ÷ 상가정보에 등록된 카페 수
```

○ 그래서 계산 결과는 "OSM이 실제의 22%를 담는다"가 아니라 **"OSM이 상가정보 대비 22%를 담는다"**로 해석해야 함. 상가정보 자체의 누락까지 보정한 실제 포착률은 이 계산만으로 알 수 없음. 이 한계가 다음 절의 분석에서 드러남

## 7. 누락의 방향: 무작위가 아니다

□ 6절은 누락의 크기를 측정함. 이 절은 그 누락이 무작위 잡음인지, 지역에 따라 달라지는지를 구분함  
 ○ 구분이 중요한 이유 — 무작위라면 여러 동을 합쳐 영향을 줄일 수 있지만, 지역에 따라 달라진다면 특정 지역의 포착률이 체계적으로 낮아져 지역 비교 자체가 왜곡됨

## 8. 지도에 "0개"로 표시되면 실제로도 0개인가

### 8.1 사후확률: 지도에 0개로 표시된 결과를 얼마나 믿을 수 있는가

○ 예를 들어 상가정보에는 서점이 있지만 OSM에는 0개로 표시될 수 있음. 이때 상가정보의 점포 수를 이미 신뢰한다면 실제 점포 수는 상가정보로 확인할 수 있으므로, 그 동의 실제 공백 여부를 알기 위해 사후확률을 계산할 필요는 없음  
○ **사후확률**은 OSM만 사용해야 하는 상황에서 의미가 있음. 지도에 0개로 표시된 결과를 본 뒤, 실제로도 0개일 확률을 계산하여 OSM의 0개 관측을 공백으로 판단해도 되는지 평가함  
○ 사후확률은 상가정보를 참값으로 확정하는 값이 아님. 상가정보에서 추정한 포착률과 점포 분포를 전제로 하므로, 상가정보의 한계와 해당 포착률이 다른 지역에도 적용된다는 가정을 함께 기록해야 함  
○ 포착률이 p인 자료에서 점포 하나가 지도에 표시될 확률을 p로 보면, 실제 점포가 N개인 동이 지도에 0개로 표시될 확률은 (1−p)ᴺ임

□ **서점**(실측 포착률 0.074)을 사용해 계산함  
 ○ 이 포착률의 분자는 OSM에서 확인된 서점 113개이고, 분모는 상가정보에 등록된 서점 1,524개임. 따라서 `113 ÷ 1,524 = 0.074`이며, 이후 계산은 상가정보에 등록된 서점이 OSM에 표시될 확률을 0.074로 가정함  
 ○ 실제 서점이 3개인 동이 지도에 0개로 관측될 확률: (1−0.074)³ = 0.926³ = **0.794** — 실제 서점 3개가 모두 누락될 확률은 79.4%임  
 ○ 서점이 10개여도 0.926¹⁰ = 0.462 — 실제 점포가 있어도 약 절반이 공백으로 관측됨

○ 관악구 전체에서 측정한 포착률을 신림동의 사후확률 계산에 사용할 수는 있지만, **신림동에도 관악구 평균 포착률이 적용된다는 가정**이 필요함  
 ○ 같은 기간·업종 분류를 사용하고, 신림동의 점포 밀도·상권 특성·지도 등록 방식이 관악구 평균과 크게 다르지 않아야 함  
 ○ 신림동의 상가정보와 OSM을 모두 확보했다면 신림동 포착률을 직접 계산하는 것이 우선임. 관악구 포착률을 대신 쓰는 경우에는 실제 신림동 포착률이 아니라 관악구 평균을 적용한 추정값으로 표시함  
 ○ 관악구 포착률보다 낮거나 높은 값을 함께 대입해 사후확률의 범위를 제시해야 함. 이 장에서 확인한 지역별 포착률 차이를 무시하고 관악구 값을 신림동에 그대로 적용하면 불확실성을 과소평가할 수 있음

○ 여기에 "애초에 서점이 0개인 동이 얼마나 되는가"(사전확률, 상가정보 기준 P(N=0) = 0.118)를 반영해 베이즈 규칙으로 계산하면, **0개로 관측된 동이 실제로 0개일 확률**(사후확률)을 얻음

```
P(진짜 0개 | 0개로 보임) = P(N=0) ÷ Σₙ P(N=n)·(1−p)ⁿ
```

○ 서점의 사후확률은 **0.150** — **지도에 서점이 0개로 관측된 동 일곱 곳 가운데 여섯 곳은, 서점이 있지만 등록되지 않은 경우임**

□ 코드는 포착률을 변경하면서 사후확률이 어떻게 변하는지도 함께 기록함(`[C-1]` 구간)

○ 표 해석 방법 — **실측 포착률**은 6절에서 계산한 관측값이고, **필요 p\***는 "0개 관측을 실제 공백으로 판정하려면 포착률이 최소 얼마여야 하는가"를 나타내는 판정 기준임. 실측값이 필요 p\*보다 낮으면 그 업종군에서는 0개 관측으로 공백을 판정할 수 없음

□ 일곱 업종군 모두에서 판정 불가가 나오지만, 그 사유는 두 가지로 구분됨  
 ○ **첫째 경우 — 포착률이 부족한 경우.** 서점·안경·화장품·약국이 여기에 해당함. 서점은 필요 p\* 0.85에 비해 실측값이 0.074로 10배 이상 낮음  
 ○ **둘째 경우 — 질문이 성립하지 않는 경우.** 카페·편의점·미용·뷰티는 서울 425개 동 전부에 점포가 실재해 "0개인 동"이 하나도 없음. 사전확률 P(N=0)이 0이므로 사후확률도 0이 되고, 포착률을 높여도 컷라인에 도달하지 않아 필요 p\* 열은 —로 표시됨. 해당 업종에서는 "0개"라는 관측이 나오지 않으므로, 판정 대상을 0개 여부가 아니라 개수 수준으로 바꿔야 함

### 8.2 컷라인: 판단 기준은 오판 비용이 정한다

□ 사후확률이 얼마 이상이어야 결정을 내릴 수 있는가 — 이 기준선(컷라인)은 자료가 정하지 않음. **두 가지 오판이 각각 얼마의 손실을 내는지**가 결정함  
 ○ 잘못 진입하면 인테리어·권리금 같은 매몰 투자를 잃고(L진입), 진입하지 않았는데 정말 비어 있었다면 기회를 잃음(L상실). 두 기대손실이 동일해지는 지점이 컷라인임

```
q* = L진입 ÷ (L진입 + L상실)
```

□ 매몰 투자 1.0, 기회비용 0.25로 설정하면 q\* = 1.0 ÷ 1.25 = **0.80** — 실제 공백일 확률이 80% 이상일 때만 진입함  
□ 공공 결정에서는 비용의 방향이 반대임 — 시설을 놓아야 할 곳을 놓치는 손실(사각지대 방치)이 1.0이고, 공백이 아닌 곳을 한 번 더 현장 확인하는 비용이 0.25라면 q\* = 0.25 ÷ 1.25 = **0.20**  
○ 컷라인이 낮아지는 만큼 판정의 내용도 바뀜 — "진입한다"가 아니라 "의심되는 동을 현장 확인 대상으로 선정한다"  
□ **같은 지도, 같은 포착률에서도 창업 희망자는 0.80을, 구청 담당자는 0.20을 적용할 수 있음** — 1장에서 본 오류 비용의 비대칭이 여기서 컷라인이라는 숫자로 나타남

> - **컷라인은 자료가 아니라 오판 비용의 비가 정함**
> - 판정표를 보고할 때 사용한 두 손실의 비를 함께 적어야 함 — 적지 않으면 다른 목적(공공 배치)에서 그 표를 잘못 재사용하게 됨

### 8.3 등급 판정표: 동마다 결론을 부여한다

□ 마지막으로 412개 동 각각에 사용 등급을 부여함. 판정 축은 둘 — ① 사후확률(그 동의 0개 관측을 신뢰해도 되는가) ② 그 동의 포착률이 7절 회귀식의 예측에서 얼마나 벗어났는가(|z|)  
 ○ 두 축을 평가하기 전에 확인할 사항이 하나 있음 — 포착률이 1을 넘는 동은 확률로 해석할 수 없으므로 사후확률을 계산하지 않고 별도로 분류함. 1 초과를 0.999로 대체하면 대응표 불일치로 발생한 값이 오류 없이 계산을 통과해 가장 높은 등급을 받음

| 등급         | 기준                                   | 행정동 수 | 포착률 범위 | 대표 동         |
| ------------ | -------------------------------------- | --------: | ----------: | --------------- |
| 그대로 사용  | 포착률 ≤ 1, 사후확률 ≥ 0.80            |         1 |       0.857 | 교남동          |
| 보정 후 사용 | 포착률 ≤ 1, 사후확률 < 0.80, \|z\| ≤ 2 |       248 | 0.089~0.471 | 가산동, 신사동  |
| 사용 금지    | 포착률 ≤ 1, 사후확률 < 0.80, \|z\| > 2 |       162 | 0.000~0.704 | 역삼1동, 서교동 |
| 대응표 점검  | 포착률 > 1                             |         1 |       1.069 | 가회동          |

○ **그대로 사용**은 412개 중 교남동 1곳뿐임(포착률 0.857) — 지도만으로 공백을 판정해도 되는 동은 서울에서도 예외적임  
○ **보정 후 사용**은 포착률이 낮지만 회귀식이 예측하는 수준인 동 — 관측 개수를 예측 포착률로 나눠 실제 개수를 추정한 뒤 사용함. 예측 포착률 0.20인 동에 3개가 관측되면 3 ÷ 0.20 = 15개 안팎으로 추정하고 판단함 참고) |z|는 각 행정동의 실제 포착률이 회귀식의 예상 포착률에서 얼마나 벗어났는지를 나타내는 표준화 잔차이다.
○ **사용 금지**는 포착률이 낮으면서 예측에서도 크게 벗어난 동 — 보정식을 적용할 근거가 없으므로, POI만으로 판정하지 않고 다른 자료를 결합하거나 현장을 확인함  
○ **대응표 점검**은 포착률이 1을 넘어 확률로 해석할 수 없는 동임 — 가회동은 분모 101개 중 카페가 58개인데 OSM 카페는 75개임. 관광지에서 상가정보의 다른 소분류로 등록된 점포가 OSM에서는 `amenity=cafe` 하나로 분류되면 분자만 증가함. 등급을 부여하지 않고 해당 업종군의 대응 규칙을 다시 설정한 뒤 재집계함

○ 이 결과가 2절 질문의 최종 답임 — **서울 412개 동 가운데 지도 자료만으로 "비어 있다"를 판정할 수 있는 동은 1곳뿐임.** 248개는 보정을 적용해야 하고 162개는 다른 자료가 필요하며, 1개는 대응표를 다시 설정해야 함

## 9. 핵심 요약

○ **"자료에 없다"와 "현실에 없다"는 다른 말임.** 지도의 카페 두 곳은 "실제로 두 곳"일 수도, "추가 점포가 있지만 등록되지 않은 상태"일 수도 있으며, 지도만으로는 구분할 수 없음 (2절)  
○ **자료는 두 부류로 나뉨.** 센서가 관측하는 자료(위성영상)는 그 자체가 관측 전체이고, 사람이 등록하거나 결제 수단에 기록되는 자료(POI·카드 매출)는 현실의 일부만 담음. 포착률 측정과 등급 판정은 뒤의 6·7단계에만 적용함 (3절)  
○ **STAC는 위성영상을 검색하는 공통 규격.** Catalog → Collection → Item → Asset의 포함 관계이며, Item은 파일이 아니라 색인임. 실시간 카탈로그 조회는 재현되지 않으므로 검색 조건과 Item ID를 기록함 (4절)  
○ **부분 읽기는 필요한 조각만 받는 구조.** 268.5MB 파일에서 관심 영역 0.048%만 1.44초에 전송받았고, 전체 파일은 한 번도 저장되지 않았음. 포맷은 자료의 차원 구조가 정함 — 2차원 래스터는 COG, 시계열은 Zarr, 벡터 테이블은 GeoParquet (5절)  
○ **포착률은 기준 자료 대비 비율임.** 서울 OSM POI는 상가정보 대비 0.227, 즉 약 5분의 1만 포함함. 포착률이 1을 넘으면(미용·뷰티 1.249) 자료가 아니라 대응표의 문제이며, 계산식이 아니라 대응표를 수정함 (6절)  
○ **누락은 무작위가 아님.** 도심에서 멀수록 포착률이 체계적으로 낮아지며(계수 −0.3089), 대응표를 바꾸면 이 결론 자체가 달라질 수 있으므로 대응표를 결과와 함께 공개함. 절대 수준보다 동 사이의 순서(순위상관 0.994)가 안정적임 (7절)  
○ **"0개로 보임"과 "실제로 0개"는 확률로 연결됨.** 서점 포착률 0.074에서는 0개로 관측된 동 일곱 곳 중 여섯 곳에 실제로 서점이 있음(사후확률 0.150). 판단 기준선인 컷라인은 자료가 아니라 오판 비용의 비가 정함 — 출점 결정 0.80, 공공 배치 0.20 (8절)  
○ **서울 412개 동 가운데 지도만으로 공백을 판정할 수 있는 동은 1곳뿐임.** 248개는 보정(관측 ÷ 예측 포착률) 후 사용하고, 162개는 다른 자료나 현장 확인이 필요함 (8.3절)

## 10. 과제

□ 이번 장의 과제는 **자료를 어디까지 신뢰할지 숫자로 판단하는 것**  
○ 한 줄 명령으로 제출할 파일을 생성함

```bash
python scripts/submit.py 3 --id 학번 --name 이름
```

□ 이 명령이 자동으로 처리하는 작업: 자료 준비(`3-0b-commercial-bias-data-prep.py`) 실행, 대표 실습 `3-4-commercial-data-bias.py` 실행, 제출용 파일 생성  
 ○ 실행이 완료되면 `submissions/` 폴더에 `제출_3장_학번.md` 파일이 생성되고 실행 결과가 포함됨  
 ○ **확인할 항목은 업종별·동별 포착률과 1을 넘는 값의 존재 여부임**

○ 마지막의 빈칸 세 개를 작성함

1. 주목한 숫자 하나를 그대로 기록하고, 주목한 이유를 한 문장으로 작성
2. 그 숫자가 왜 그렇게 나왔는가
3. **지도에 점포가 하나도 없는 동네가 있다. "여기는 비어 있으니 창업하자"고 말해도 되는가? 근거를 숫자로 제시하라.**

□ **3번이 이 과제의 핵심.** 답에는 포착률·사후확률·컷라인 가운데 적어도 두 개가 숫자로 들어가야 함 — 6~8절의 분석 결과를 근거로 사용함  
 ○ 과제의 핵심은 숫자 산출이 아니라 그 숫자를 근거로 판단하는 능력

○ 작성한 파일 **하나만** 업로드하면 제출이 완료됨

> - **실행에 실패해도 제출함**
> - 실행 중 오류가 발생하면 오류 메시지가 그 파일에 자동으로 기록되고, 질문이 "어느 단계에서 실패했는가"로 바뀜
> - 실패 원인을 기록한 제출도 정상 제출로 인정함. 실행 성공 여부로 점수를 매기지 않음

> - **이 장의 대표 실습은 난수를 쓰지 않음**
> - 미리 준비된 자료를 그대로 집계하므로 교재에 적힌 값이 출력되어야 정상이고, 다른 실행 결과와도 동일함
> - 다만 STAC 검색(`3-1`)은 라이브 카탈로그 조회라 시점에 따라 개수가 달라질 수 있음 — 대표 실습(`3-4`)에는 해당하지 않음
